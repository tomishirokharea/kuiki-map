# 画面側の期限計算が、未来の完了日を「完了」と数えないようにする　設計（短い版）　2026-11-20

承認：R A さん（2026-11-20・案1と知らせ方「既存の場所で知らせる」を選択）
前の作業：`2026-11-20-s13-naosu-miraibi-design.md`（この課題はそこで F2 として見送ったもの）

## 1. なぜ

前の作業で、未来の完了日を **入力・帯の集計・自動の確かめ** の3層で止めた。しかし全体監査が、**画面側は今も未来の完了日を「完了」として数える**ことを見つけた。

- `lastDone`（schedule.js:122）は `t.completedAt`・`t.paperDone`・S-13 の全 `x.c` の**最大値**を取るだけで、上限がない
- `c = 2026-12-31` だと `daysFrom` が負になり、`left = YEAR - daysFrom > 365` → `st: 'ok'`
- その結果、**完了日が未来日しかない区域**は「順調」と出て、`coverInfo().covered` に数えられ、ホームの「会衆で区域の◯%」が膨らむ

**§1 の訂正：区域61-7 で実際に変わること**（はじめに書いていた「61-7 は今も『順調』と出て `covered` に数えられ、％が膨らむ」は**まちがい**。下が正しい）

区域61-7 は `kind:'p'` の 2026-04-05（本物の完了日）と、`kind:'a'` の 2026-12-31（10-31 の打ちまちがい）の両方を持つ。本物の過去の完了日があるので、**この直しの前も後も `st:'ok'` で、`covered` に数えられる**。「順調」の文字と会衆の割合は変わらない。

変わるのは**期限の日付**で、`2027-12-31 → 2027-04-05`。12か月のグラフの外にいた区域が、中にもどる。「順調」の判定と会衆の割合が変わるのは、**完了日が未来日しかない区域**だけ（61-7 はその形ではない）。

## 2. 目的・しないこと

**目的**
- 画面の期限・区域の状態・会衆の割合が、未来の完了日を「回り終えた」と扱わない
- 係が**入力ミスに気づいて直せる**（直す手段は前の作業で作ったポップ）

**しないこと**
- `syncPaperDone` と `t.paperDone` の書き込みを変えること。**S-13 の表には、間違った日付をそのまま見せ続ける**（見えなければ直せない）
- 新しいタイル・画面・設定を作ること
- サーバー側（前の作業で対応済み）
- **年1回の期限の計算のほかに、未来の完了日を読むところ**（下の「残っている課題」の3つ）。貸し出し・続きからの判定で、取り消しが起きたことのあるところなので、別の課題として、それ用の試験と一緒に直す

**この直しが届く範囲（はっきりさせておくこと）**

直したのは**年1回の期限の計算（`lastDone`・`dueInfo`・`coverInfo`）と、その結果を見せる画面**（「前回の記録なし」の一覧・毎月の点検・係の区域一覧の「前回回り終えた日」）だけ。**画面のすべてが未来日に対して安全になったわけではない。**

## 2b. 残っている課題（この直しでは直していない・別の課題）

次の3つは、今も未来の完了日を「完了」として読む。**どれもこの直しで新しく壊れたものではなく**（前からこうなっている）、貸し出し・続きからの判定にかかわるため、わざと手をつけていない。

| # | 場所 | 今どうなるか |
|---|---|---|
| F-a | `lastBackOf`（app.js:8728-8732） | 区域をもらう画面（`openRequestSheet`）で「前回返却した日 2026/12/31」と出る。「返却から長い順」（`byLongest`）の並びもずれる |
| F-b | `autoFreeOf`（app.js:8710-8713） | `daysSince(未来日)` が負になるので、打ちまちがいのある区域が「自動受け取り」から黙って外れる（係にも伝道者にも理由が見えない） |
| F-c | `isPartial`（schedule.js:567）・`contAvail`（app.js:9733）・`canCont`（tsuzuki.js:31） | 未来日があると、途中の返却が「完了」として扱われる（続きから回る案内が出なくなる） |

直すときは、`tsuzuki-p6`・`autofree`・`kaiki` の回帰と、F-a/F-b/F-c それぞれの新しい試験を先に用意する。

**失敗とみなすこと**
- 間違った日付が画面から見えなくなり、係が直せなくなる
- 「前回の記録なし」と「完了日が未来」が見分けられない
- `lastDone` を使うほかの場所（おすすめ・区域カードの優先・カルテ）が壊れる

## 4. 作るもの

1. **`lastDone`（schedule.js:122）**：候補から「今日より後」を除く。今日は含める
2. **未来の完了日を持つ区域を返す小さな関数**（知らせ用）
3. **「前回の記録なし」のタイル・一覧（schedule.js:376・427）**：その区域を区別し、「完了した日付が未来になっています」と出す。**新しいタイルは作らない**。既存の一覧の中で文言を分け、既存の「S-13を開く」ボタンで直しに行ける
4. **点検（schedule.js:1757）**：1項目足す。**その行に「S-13を開く」ボタンを付ける**（未来日と過去日の両方を持つ区域は「前回の記録なし」の一覧に出ないので、この行からしか直しに行けない。ボタンは既存の `data-tls13` と `openS13()` をそのまま使う）
   - **係の区域一覧の「前回回り終えた日」（`lastDoneTxt`・app.js:8734）**：`t.paperDone` が未来で落ちたときは、S-13 にある**今日までの完了日**（`KM.dueInfo(t).last`）に落ちる。期限の画面・点検と同じ日付になる。S-13 は係のスマホにだけあるので、**伝道者のスマホの出かたは変えない**（`D().s13` が空なら今までどおり）
5. スペイン語（`i18n-es.js`）・版・`sw.js`
6. 試験：`lastDone`・`dueInfo`・`coverInfo` の回帰と、知らせが出ること
